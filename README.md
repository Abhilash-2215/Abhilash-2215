### Folder structure improvements (general standard)
```
project-name/
├── src/               # source code
├── public/ or assets/ # static files
├── tests/             # unit/integration tests
├── docs/              # additional documentation, architecture diagrams
├── .gitignore
├── LICENSE
├── README.md
└── package.json / pom.xml (as applicable)
```

### Commit message conventions
Adopt **Conventional Commits**:
```
feat: add snake collision detection
fix: correct score reset bug on game over
docs: update README with setup instructions
refactor: extract game loop into separate module
test: add unit tests for score calculator
chore: update dependencies
```

### Branch strategy
For solo/learning projects, a lightweight strategy is enough:
- `main` — always deployable/stable
- `dev` — active development
- `feature/<name>` — individual features, merged into `dev` via PR, then `dev` → `main` when stable

This is simple but **shows recruiters you understand branching discipline**, which matters more than the specific model chosen.

### Licensing recommendation
Use **MIT License** for all personal/learning projects — it's the most recognized, permissive, and recruiter-neutral choice. Add a `LICENSE` file to every public repo (GitHub lets you generate this in two clicks when creating a repo).

## 5. GitHub Actions Workflow Recommendations

### Java (Spring Boot / Maven) — Build & Test
```yaml
name: Java CI

on:
  push:
    branches: [ main, dev ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: Build with Maven
        run: mvn -B clean install
      - name: Run tests
        run: mvn test
```

### React (Frontend) — Build & Lint
```yaml
name: React CI

on:
  push:
    branches: [ main, dev ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint --if-present
      - run: npm run build
      - run: npm test --if-present -- --watchAll=false
```

### Node.js Backend — Test & Build
```yaml
name: Node Backend CI

on:
  push:
    branches: [ main, dev ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test
```

### Code Quality (ESLint + Prettier check)
```yaml
name: Code Quality

on: [push, pull_request]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npx eslint . --max-warnings=0
      - run: npx prettier --check .
```

### Deployment (example: Netlify via CLI, adapt secrets as needed)
```yaml
name: Deploy to Netlify

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci && npm run build
      - name: Deploy
        uses: nwtgck/actions-netlify@v2
        with:
          publish-dir: './build'
          production-branch: main
        env:
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}
```

> Store all tokens/secrets in **Repo Settings → Secrets and variables → Actions**, never hardcode them.
